  1. 这些 words 是从互联网加载的，所以如果网络连接不好，它们可能需要一点时间才能可用。下面这个很酷的 view modifier 可能能帮助处理初次启动时可能出现的“延迟”。你可以把这个 view modifier 应用到主游戏 View 的 var body 里几乎任何一个 View 上（例如最顶层的 VStack）。当 words 这个 @Environment 变量真正被更新并且里面有一些单词时，它会做出响应（也就是从网络下载完成之后；这可能耗时几毫秒、几秒，或者如果网络断了就永远等不到）。这也展示了如何从 words 中取出指定长度的随机单词。
.onChange(of: words.count, initial: true) {
    if game.attempts.count == 0 { // 不要打断正在进行的游戏
        if words.count == 0 { // 还没有 words
            game.masterCode.word = "AWAIT"
        } else {
            game.masterCode.word = words.random(length: 5) ?? "ERROR"
        }
    }
}

注意，如果 onChange 在游戏已经开始之后（game.attempts.count > 0）才发现 words 到达，那么你就会继续玩以 AWAIT 为答案的那局。还要注意，一旦 words 已经到达，如果找不到长度为 5 的单词（理论上不该发生，但谁知道呢！），用户会玩到以 ERROR 为答案的游戏。

这个 onChange(of:) 只会激活两次：游戏 View 第一次出现时（因为有 initial: true），以及 Words.swift 完成加载一些 words 时（words.count > 0）。所以在其他所有需要 master code 的时候（例如游戏重开时），你都必须自己从 words 里取（上面的代码不会替你完成）。

希望到用户点击 restart 的时候，words 已经从网络加载完成；但如果还没有，你需要做一些合理处理（有点像上面的 onChange 在启动阶段尝试做的那样）。

最后，请注意这个 onChange(of:) 假设单词长度是 5。当你支持 3、4、6 个字母的单词时，需要相应调整。

评分标准

在本季度的所有作业中，目标都是写出高质量代码，让它能够在没有警告或错误的情况下构建，然后测试生成的应用，并不断迭代直到它能正常工作。

下面是作业被扣分最常见的原因：

  • 项目无法构建。
  • “必做任务”部分中的一个或多个项目没有完成。
  • 没有理解某个基础概念。
  • 项目无法在没有警告的情况下构建。
  • 代码在视觉上很潦草、难以阅读（例如缩进不一致等）。
  • 因为缺少注释、变量/方法命名差、解法结构差、方法过长等原因，你的解答让阅读代码的人难以（或不可能）理解。

学生经常问：“我到底需要给代码写多少注释？”答案是：你的代码必须能让任何阅读它的人轻松、完整地理解。你可以假设读者知道 iOS API，也知道课堂中 Code Breaker 游戏代码的工作方式，但不应该假设他们已经知道你（或任何人）对这个作业的解法。
