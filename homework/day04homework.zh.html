提示

  1. 必做任务 3 的初始版本，大概只需要四行左右的代码就能实现。
  2. 有点出人意料的是，必做任务 4 几乎不需要改动你的 UI（除了改变创建 CodeBreaker 游戏的方式，因为现在需要把某局游戏应有的 peg 数量参数化）。部分原因是你在作业 1 中已经做过相关工作，另一部分原因则只是 ForEach 很强大。
  3. 你的 Model 中的 init 函数现在很可能需要接收游戏中的 peg 数量。
  4. 为了实现必做任务 5，你需要生成一个 3 到 6 之间的随机数。可以用 Int.random(in: 3...6)。
  5. Peg 目前被 typealias 成 Color。现在 peg 既可能是 emoji（String），也可能是 Color，所以这样不行了。一个简单方案？让 Peg 成为 String，并用名字表示颜色（例如 "red" 或 "blue"）。如果某个 Peg（String）不是你支持的颜色之一，就把它当成 emoji。
  6. 如果 Peg 不再是 Color，你的 Model 就可以改回 import Foundation，不用再使用当 Peg 是 Color 时被迫引入的 import SwiftUICore（或 SwiftUI）。因为 Model 本来就应该独立于 UI，不导入任何 UI 模块会让人舒服得多，也能降低我们把本该属于 UI 的代码放进 Model 的可能性。
  7. 你很可能会希望显示 emoji 的 Text 尺寸是灵活的（就像彩色圆点 peg 一样）。一个简单做法是让这个 Text 成为 Circle（或 Rectangle）的 .overlay，并给它应用 .font(.system(size: 120)) 和 .minimumScaleFactor(9/120) 修饰器。这样 Text 会为自己选择一个不大于 120 点、不小于 9 点的字体。并且因为它是 .overlay，它的布局会完全继承自尺寸灵活的父视图（例如 Circle），所以它本身也会在尺寸上变得灵活。
  8. 要在两种游戏类型（emoji 或彩色圆点）之间随机选择，你大概会想要一个随机的 Bool 值。Bool.random() 会给你一个。
  9. 你可以只支持目前一直在用的颜色（"blue"、"green"、"red"、"yellow"），但稍微更扩展一点的方案，是把自己限制在 Color 结构体内置的颜色范围内。下面的 Challenge Mode 会说明你可以怎么做。

评分标准

在本季度的所有作业中，目标都是写出高质量代码：代码可以无警告、无错误地构建，然后对生成的应用进行测试，并不断迭代，直到它能正常运行。

下面是作业最常见的扣分原因：

  • 项目无法构建。
  • “必做任务”部分中有一个或多个条目没有满足。
  • 某个基础概念没有被理解。
  • 项目不能在无警告的情况下构建。
  • 代码在视觉上凌乱，难以阅读（例如缩进不一致等）。
  • 由于缺少注释、变量/方法命名不佳、解法结构不佳、方法过长等原因，你的解答让读代码的人难以（甚至不可能）理解。

学生经常会问：“我的代码到底需要写多少注释？”答案是：你的代码必须能让任何阅读它的人轻松、完整地理解。你可以假设读者了解 iOS API，也了解课堂上 CodeBreaker 游戏代码的工作方式；但不应该假设他们已经知道你（或任何人）对这份作业的解法。

Challenge Mode

Challenge Mode 是一个机会，让你扩展本周学到的内容，并用更难的练习挑战自己。强烈建议你每周都尝试其中一个或多个，以便从这门课中获得更多收获。

  1. 2 分。借助 AI 的帮助，扩展你的游戏能够支持的颜色范围：除了 "blue"、"red"、"green" 和 "yellow" 之外，至少要包含 Color 结构体中的所有内置颜色（例如 Color.brown、Color.pink 等）。

    遗憾的是，Color 结构体并不支持通过名字访问它的内置颜色，但你可以请你选择的某个 AI 写一些代码，根据颜色名字得到一个 Color（以及反过来）。比如这样问："create a failable initializer for Color which takes a color name and translates it into one of Color's built-in static colors"。希望你的 AI 会给你一段 Color 结构体的 extension，其中包含一个能解决问题的 init?！

    你也可以继续追问它："now create an Optional var called name which does the inverse"（虽然完成这个 Challenge Mode 并不绝对需要这样的东西，但在某些解法中它可能会派上用场）。

    一定要检查 AI 的成果！有时候它会产生幻觉，编造出实际上并不是 Color 中 static var 的颜色。另外，有些 AI 比另一些更聪明，所以如果你从某一个那里得不到想要的结果，可以试试别的。

    如果你的 AI 成功完成了这件事，它有希望让 init（以及 name var）返回 Optional（因为当某个名字没有对应的 Color，或反过来没有对应名字时，它需要返回 nil）。这是一个很好的机会，可以确认你理解 Optional 是如何工作的。

    如果一切顺利，并且取决于你的 AI 写出了什么，你应该能写出类似这样的代码……

    if let color = Color(name: peg) { /*color pegs*/ } else { /*emoji pegs*/ }.

    或者也许是这样？ let color = Color(name: peg) ?? .clear

    通过在游戏重启时使用不同颜色来测试你的代码。如果你能做到这一点，那么你已经很好地走在完成下一个 Challenge Mode 的路上了……

  1. 1 分。当你重启游戏时，从多种不同的 emoji（或颜色）集合中选择一组来使用（我们把这称为游戏的“主题”）。例如，某次重启时你可能使用表情主题（😀 🤪 🥳 😨），下一次使用大地色系，再下一次使用交通工具 emoji（🚗 🚲 🛩 ⛵），再下一次使用标准颜色，等等。

  2. 1 分。为上面 Challenge Mode 2 中加入的各种主题命名（例如 “Faces” 或 “Earth Tones”），并把这个名字作为游戏标题显示在屏幕上的某个位置。

    对于这一项，你可能会发现自己想构建一个同时使用 Array 和 Dictionary 的数据结构；不过你需要理解 Optional 才能使用 Dictionary，因为在 Dictionary 中查找某个东西会返回一个 Optional（这很合理，因为有时候你想从 Dictionary 里取出的东西可能根本不在里面）。

    这个 Challenge Mode 大概只需要几行代码（不包括把各种 emoji/颜色主题加载进去的那些代码行）。

    你可能必须把其中一个主题硬编码为应用启动时首先显示的主题（除非你想真的大胆一点，试着弄明白如何使用 .onAppear 在游戏第一次出现在屏幕上时随机选择一个主题）。

    这里还可以采用一个额外的简化假设：至少有一个众所周知的主题保证始终存在（也就是应用首次启动时出现的那个主题）。有了这些假设，你就可以更频繁地使用“强制解包”（也就是 !），而不必总是检查一次 Dictionary 查找返回的值是不是 nil。例如，你可以假设 themes.keys.randomElement() 永远不会返回 nil（如果 themes 是你的主题 Dictionary），并且 themes["Mastermind"]! 永远不会崩溃。否则，当你的游戏第一次出现而又没有可用主题时，你可能会陷入一点麻烦！
